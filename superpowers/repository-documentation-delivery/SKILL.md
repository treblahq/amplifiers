# Repository Documentation Delivery

## Mandate

Turn a repository into a clearer open-source surface with stronger entry-point
documentation, better contribution guidance, and cleaner writing standards.

## When to Use

- Improving a root `README.md`
- Writing or restructuring `CONTRIBUTING.md` or a project-wide writing standard
- Creating project indexes or documentation navigation
- Polishing documentation that feels technically correct but clumsy to read

---

## Workflow

1. Inspect the repository structure, public entry points, and existing docs
2. Decide which files should own which explanations
3. Write or reorganize the documentation with factual, modular content
4. Rewrite awkward or robotic passages into direct natural English
5. Use GitHub-friendly markdown or HTML only where layout control adds value

---

## Input Checklist

Before starting, collect:

1. What is the repository for?
2. Which docs are entry points and which are support files?
3. What is currently confusing, redundant, or visually weak?
4. Which repository concepts need to be explained together?

---

## Output Standard

Deliver where possible:

1. A clearer README structure
2. Better contribution or writing guidance
3. A cleaner documentation ownership model
4. Natural, direct prose without AI-sounding filler
5. Minimal HTML usage for presentation control when markdown alone is not enough

---

## Composition Rules

- Use knowledge writing to define the documentation structure and ownership
- Use humanized writing to remove robotic phrasing and weak filler
- Use HTML architecture only for safe GitHub-native markup decisions
- Use product design judgment to improve hierarchy and first impression
