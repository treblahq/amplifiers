# VSL Frameworks (Video Sales Letter)

> **Objective:** Choose and apply VSL structures by context (cold/warm/hot) while keeping clarity and proof.

## Overview

This document is a focused playbook on **VSL Frameworks (Video Sales Letter)**.

Primary job: choose and apply VSL structures by context (cold/warm/hot) while keeping clarity and proof.

- Focus: generate pattern interrupts that win attention *fast*, then earn belief with proof.
- Focus: packaging and framing — the offer is the conversion engine (not the page design).
- Focus: reduce friction, increase trust, and keep message-match from ad → page → decision.

## Key concepts

- Classic structures (PAS, Story, Mechanism-first)
- When to use each structure (time, proof, channel)
- How to organize: hook → belief → mechanism → proof → offer
- How to write for speech (spoken language)
- How to place CTAs and a delay button
- Common mistakes: too long, over-explaining, over-promising

## Execution framework

1. **Define the promise and available proof level**
   - Intent: Collect real proof (screenshots, numbers, demos) and place it with context.
   - Output: A proof pack: 3–10 assets (screenshots, numbers, demos) mapped to key claims.
   - Pitfall: Using proof with no context (no baseline, timeframe, or attribution).
2. **Choose the structure (PAS/Story/Mechanism-first)**
   - Intent: Use story as proof and a bridge: keep it tight, map it to mechanism/proof, and point to the next step.
   - Output: A story bank: 3–5 short stories mapped to objections, proof points, and the CTA.
   - Pitfall: Long stories with no mechanism/proof bridge — people watch/read, but belief and action don’t increase.
3. **Write the hook (0–10s) with tension/curiosity**
   - Intent: Write a one-line pattern interrupt that creates tension/curiosity; generate variations and test.
   - Output: 10–25 hook lines, tagged by driver/angle, each with 1 suggested proof asset.
   - Pitfall: Writing “clever” lines without a clear promise, audience, or proof.
4. **Build belief: problem, myth, mechanism**
   - Intent: Create tension with contrast (before → after, myth → truth, common → uncommon) and keep it concrete and provable.
   - Output: A pain map: symptoms → consequences → desired state, plus a language bank.
   - Pitfall: Describing the problem at a surface level (symptoms) without consequences and real context — it doesn’t feel urgent.
5. **Insert proof and demonstration before the pitch**
   - Intent: Collect real proof (screenshots, numbers, demos) and place it with context.
   - Output: A proof pack: 3–10 assets (screenshots, numbers, demos) mapped to key claims.
   - Pitfall: Using proof with no context (no baseline, timeframe, or attribution).
6. **Present the offer (stack + guarantee) and CTA**
   - Intent: Define one next step and phrase it as verb + outcome + what happens next; repeat it at the right moment.
   - Output: An offer stack with function-based bonuses + guarantee + real conditions.
   - Pitfall: A vague or overly broad guarantee — it increases refunds and attracts the wrong buyers.
7. **Cut and edit for rhythm (fewer connectors)**
   - Intent: Edit for clarity and scanability: one idea per paragraph, short lines, tight transitions, and proof preserved.
   - Output: An edited draft: shorter paragraphs, clearer headings, preserved proof, and one primary CTA.
   - Pitfall: Over-editing until you remove proof and clarity — the asset reads “clean” but stops converting.

## Templates and examples

```text
VSL (macro):
Hook → Problem → Myth → Mechanism → Proof → Offer → Guarantee → CTA
```

## Common mistakes

- too long
- over-explaining
- over-promising
- Confusing *hook* (opening line) with *angle* (persuasion thesis).
- Writing hooks that don’t imply a promise or tension (they read like facts).
- Not pairing hooks with proof assets (so CTR is driven by hype, not belief).
- Saving hooks without tags (driver, stage, avatar, proof type) — the library becomes unusable.
- An aggressive promise without a mechanism (refund magnet).
- Fake urgency/scarcity (short-term CVR, long-term brand damage).
- Bonuses that compete with the core (decision friction).

## Tests and measurement

### Metrics

| Metric | What it indicates | How to use |
|---|---|---|
| 3s hold / Thumbstop | Opening strength | Iterate hook category + first frame; keep it 1 line. |
| CTR | Hook + promise match | Test angles/promise specificity; pair with proof. |
| Page CVR | Sales-stage conversion | Improve proof placement, readability, and offer clarity. |
| Scroll depth | Argument flow | Reorder sections; add subhead clarity; remove friction. |
| 25%/50% watch rate | Retention | Tighten the first 60s; reduce fluff; strengthen proof cadence. |
| CTA click rate | Pitch clarity | Align CTA to promise; place the button at the pitch moment. |

### Tests

- Test 5 hook categories on the same angle (keep offer constant).
- Test promise specificity: vague vs specific (number/timeframe/criteria).
- Test proof-first vs promise-first openings (especially on warm traffic).
- Test bonus naming: functional name vs “high perceived value” name (same bonus).
- Test stack order: objection-first bonuses vs acceleration-first bonuses.
- Test value anchoring sequence: alternatives/cost-of-inaction before price vs after.
- Test proof placement: proof before mechanism vs after mechanism.
- Test CTA timing: earlier button reveal vs later (keep script constant).
