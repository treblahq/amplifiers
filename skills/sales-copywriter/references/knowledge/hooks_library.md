# Hooks Library

> **Objective:** Build a hook library to accelerate ideation and testing (ads and content).

## Notes

- This document includes an extra section with dozens of ready-to-adapt hook templates.

## Overview

This document is a focused playbook on **Hooks Library**.

Primary job: build a hook library to accelerate ideation and testing (ads and content).

- Focus: generate pattern interrupts that win attention *fast*, then earn belief with proof.

## Key concepts

- Hook categories (curiosity, warning, contrarian, proof, identity)
- How to adapt hooks to your mechanism and proof
- How to avoid generic hooks
- Variations by format (UGC, facecam, screen, meme)
- How to create hook families from winners
- How to document hooks by angle

## Execution framework

1. **Choose 1 angle and 1 psychological driver**
   - Intent: Pick one persuasion thesis (driver + promise + proof) and keep it consistent across the asset.
   - Output: 1–3 angles (theses) with: driver → promise → mechanism → proof → CTA.
   - Pitfall: Mixing multiple angles in the same asset (no single persuasion thesis).
2. **Pick a hook category (e.g., warning)**
   - Intent: Write a one-line pattern interrupt that creates tension/curiosity; generate variations and test.
   - Output: 10–25 hook lines, tagged by driver/angle, each with 1 suggested proof asset.
   - Pitfall: Writing “clever” lines without a clear promise, audience, or proof.
3. **Write 10 short variations (1 line)**
   - Intent: Turn winners into a family: new openings, proof variants, and formats while keeping the same thesis.
   - Output: A variation map: new openings + proof variants + formats, all anchored to the same thesis.
   - Pitfall: Writing generic copy (no specificity or proof) — it reads fine but doesn’t create belief.
4. **Add the mechanism in 1 sentence (if needed)**
   - Intent: Explain why it works and why it’s different from the market’s default approach.
   - Output: A 1–3 bullet explanation of *why this works* (and why the default approach fails).
   - Pitfall: Naming a mechanism without explaining how it works in plain language.
5. **Add 1 suggested proof element**
   - Intent: Collect real proof (screenshots, numbers, demos) and place it with context.
   - Output: A proof pack: 3–10 assets (screenshots, numbers, demos) mapped to key claims.
   - Pitfall: Using proof with no context (no baseline, timeframe, or attribution).
6. **Define the CTA for the stage**
   - Intent: Define one next step and phrase it as verb + outcome + what happens next; repeat it at the right moment.
   - Output: One CTA phrased as verb + outcome + next step (what happens after the click).
   - Pitfall: Competing CTAs or a CTA that doesn’t match the stage (too much friction too soon).
7. **Test and save winners to the library**
   - Intent: Define the hypothesis, variants, window, and decision criteria before running it.
   - Output: A tagged library entry: category, driver, stage, proof, and performance notes.
   - Pitfall: Saving without tags/metadata (angle, stage, proof) — the library becomes a junk drawer.

## Library (hook templates)

Use the placeholders `{TOPIC}`, `{PAIN}`, `{MECHANISM}`, `{PROOF}` etc. and generate 5–10 variations per hook before testing.

### Curiosity (gap)

- “Nobody tells you this about {TOPIC}.”
- “The real reason for {PAIN}… isn’t what you think.”
- “I tested {THING} for 7 days. Here’s what happened.”
- “If I had to start from zero in {TOPIC}, I’d do this.”
- “The difference between {RESULT} and {FAILURE} is this.”

### Warning / Danger

- “If you do {MISTAKE}, you’re making {PAIN} worse.”
- “Stop {ACTION}. Do {NEW_ACTION}.”
- “The mistake that costs the most in {TOPIC}.”
- “Before {IMPORTANT_ACTION}, watch this.”
- “This feels right. It’s sabotaging you.”

### Contrarian (myth)

- “{COMMON_BELIEF} doesn’t work. What works is {MECHANISM}.”
- “You don’t need {THING}. You need {BETTER_THING}.”
- “The problem isn’t {SYMPTOM}. It’s {CAUSE}.”
- “Everyone does {X}. That’s why no one gets {Y}.”
- “Do the opposite of this and you’ll get {BENEFIT}.”

### Proof / Demonstration

- “Look at this: {DEMO}.”
- “Before/after in {TIME}: {RESULT}.”
- “Real screenshot: {PROOF}.”
- “I’ll show you exactly how I do {TASK}.”
- “3 numbers that explain why {MECHANISM} works.”

### Identity / Status

- “If you’re {PERSONA}, this is mandatory.”
- “The difference between amateur and pro in {TOPIC}.”
- “The habit that puts you in the top 1% of {NICHE}.”
- “If you want to be seen as {IDENTITY}, do this.”
- “You’re playing the wrong game.”

### Delivery format (utility-first)

- “Instead of a course, I send you {DELIVERY} so you actually consume it.”
- “Here’s the {TOPIC} ‘newsroom’: {CADENCE} updates + what to do next.”
- “If you only have 5 minutes, this {FORMAT} is all you need.”
- “I turned {TOPIC} into a {FORMAT} you can use today: {EXAMPLE}.”
- “Stop saving videos. Use this {FORMAT}: {PROMISE}.”

### Time buying (done-for-you)

- “You don’t need more knowledge. You need someone to do {TASK} for you.”
- “If you’re stuck at {PLATEAU}, this is the fastest way out: we implement {THING}.”
- “The new market is ‘do it for me’. Here’s what we actually deliver.”
- “If you’re overwhelmed, stop adding tasks — buy time: {DFY_OFFER}.”
- “Here’s why ‘strategy calls’ don’t move the needle: implementation does.”

### How to adapt fast (rule of thumb)

- Replace `TOPIC` with the most specific pain context possible (real context).
- Replace `MECHANISM` with the method name (or 1 line that explains why it works).
- Add 1 suggested proof asset (screenshot/data/demo) per creative.
- Keep the hook to 1 line; let the creative deliver the explanation.

### Hook clarity rules (short-form survival)

- Make the first line **punchy and plot-indicative** (the viewer should instantly know what the video is about).
- Avoid opaque openers like “wait till you see this” — they don’t earn attention in short form.
- Pair audio with a visual that confirms the topic/promise (visual hooks retain better than audio-only hooks).

```text
Plot-indicative hook rewrites (examples)
Bad:  "Wait till you see this."
Good: "3 edits that doubled my watch time in 7 days."

Bad:  "You’ll never believe this."
Good: "This is why your ads die after day 3 (and how to fix it)."
```

### Visual hook patterns (show while you tell)

- Show the object of the story immediately (product, dashboard, before/after, the exact thing you’re teaching).
- Show the proof as a first frame (number, screenshot, demo result) when possible.
- Use congruent visuals (don’t use random scroll-stoppers that don’t match the plot/promise).

## Common mistakes

- Confusing *hook* (opening line) with *angle* (persuasion thesis).
- Writing hooks that don’t imply a promise or tension (they read like facts).
- Not pairing hooks with proof assets (so CTR is driven by hype, not belief).
- Saving hooks without tags (driver, stage, avatar, proof type) — the library becomes unusable.
- Testing without a hypothesis (you can’t learn).
- Scaling budget before you have creative replenishment (frequency spikes).
- Changing audience + creative + offer at once (no attribution).

## Tests and measurement

### Metrics

| Metric | What it indicates | How to use |
|---|---|---|
| 3s hold / Thumbstop | Opening strength | Iterate hook category + first frame; keep it 1 line. |
| CTR | Hook + promise match | Test angles/promise specificity; pair with proof. |
| CPA/CAC | Edge × funnel efficiency | Fix the bottleneck before scaling; compare edges on CPA, not vibes. |

### Tests

- Test edge A vs edge B with the same format (same length, same CTA) to isolate the angle.
- Test “sells” vs “scales”: keep a selling edge as a control while testing scalable variants (audiences/placements).
- Test 5 hook categories on the same angle (keep offer constant).
- Test promise specificity: vague vs specific (number/timeframe/criteria).
- Test proof-first vs promise-first openings (especially on warm traffic).
- Test one variable at a time (angle OR hook OR proof) for clean learning.
- Scale horizontally first (new audiences) before vertical budget increases.
